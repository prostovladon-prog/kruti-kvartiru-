# Резервные копии SQLite в Cloudflare R2

Бакет владельца: `voiny-epoh-backups`, Standard, публичный доступ выключен. R2-токен: Object Read & Write только для этого бакета. Account API token и его S3 credentials создаёт владелец. Access Key ID/Secret Access Key не присылать в чат и не коммитить.

## Установка на действующий VPS

Владелец выполняет от root:

```bash
git -C /opt/voiny pull --ff-only
bash /opt/voiny/tools/r2-backup-setup.sh
```

Игра не останавливается. Скрипт устанавливает Python/restic из пакетов дистрибутива, спрашивает S3 endpoint, имя бакета, Access Key ID, Secret Access Key и отдельный пароль шифрования (минимум 16 символов, два ввода). Ключи/пароль вводятся скрыто, не как часть команды. Endpoint копировать из панели R2: `https://ACCOUNT_ID.r2.cloudflarestorage.com` (для jurisdiction-бакета использовать выданный Cloudflare адрес с `.eu`/`.us`). Не дописывать бакет к endpoint.

Пароль шифрования **сохранить вне VPS**, например в личном менеджере паролей. Также сохранить имя бакета, endpoint и сведения, в каком Cloudflare-аккаунте находится хранилище. Без пароля данные restic восстановить нельзя; R2-ключ можно перевыпустить в Cloudflare. Конфиг `/etc/voiny-backup/config.json` содержит секреты, права 600/root. В GitHub его нет, в резервный архив он не включается.

Настройка считается успешной только после первой отправки зашифрованного снимка в R2 и реального скачивания/проверки восстановленной SQLite. Только затем устанавливаются почасовой таймер и еженедельное обслуживание. При любой ошибке до этого таймер не устанавливается, вывод не говорит «готово».

## Что сохраняется

Python SQLite Online Backup API создаёт согласованный снимок `/var/lib/voiny/game.db`, включая закоммиченные данные из WAL. Проверка quick_check предшествует замене локального снимка. restic шифрует данные до передачи, сохраняет только `staging/game.db` и `manifest.json` с датой/размером/коммитом; в R2 не отправляется открытая БД, весь проект или токен Telegram-бота. Стандартная политика: последние 48 часовых + 30 дневных копий, минимум три последних. Настройки игры/секреты бота хранить отдельно для полного восстановления сервера.

Снимки в restic используют дедупликацию. Оплата R2 зависит от фактического объёма и операций, бесплатный лимит не обещается заранее. Не включать Cloudflare lifecycle-удаление отдельных объектов внутри этого restic-репозитория: это разрушает связанные снимки. Очистку делает только `restic forget --prune`, с фильтром `voiny-r2-v1`/`voiny-epoh`. До неё обязательно создаётся и проверяется новая копия. Старый ежедневный локальный бэкап `/var/backups/voiny` сохраняется отдельно.

## Контроль

```bash
voiny-r2-backup status
systemctl list-timers 'voiny-r2-*'
journalctl -u voiny-r2-backup -n 30 --no-pager
voiny-r2-backup verify
```

`status` показывает дату последнего успешного бэкапа, последнего теста восстановления и результат последней операции; затем список облачных снимков. Ошибки завершают job с ненулевым кодом и видны в systemd/journal. Внешнее уведомление пока не настроено: отдельный мониторинг нужен для обнаружения полного отключения VPS. Пароли не должны попадать в отчёт или скриншот.

## Получить копию для восстановления

```bash
voiny-r2-backup restore --target /root/voiny-restore-2026-11-21
```

Команда требует новую папку, скачивает последний снимок с нужным тегом и выполняет полный integrity_check. Рабочую БД не заменяет. В выводе будет путь к восстановленной копии. Для старого снимка можно указать `--snapshot ID`. Перенос проверенной базы в `/var/lib/voiny/game.db` — отдельный шаг с остановкой сервиса, сохранением текущих DB/WAL/SHM, правильными правами и проверкой запуска. Это не делает данный скрипт.

При потере всего VPS: на новом Linux установить restic/Python, получить код из GitHub, выполнить `python3 /opt/voiny/tools/r2_backup.py configure`, ввести сохранённый **тот же** пароль и новые/сохранённые R2 credentials, затем выполнить `python3 /opt/voiny/tools/r2_backup.py restore --target /root/voiny-restore` до запуска игры. Не запускать `setup` на пустой/неверной базе: для восстановления сначала нужен доступ к существующему репозиторию, а не первая отправка новой базы. Не загружать конфиг в GitHub.

Документация: [SQLite Backup API](https://www.sqlite.org/backup.html), [R2 S3 credentials](https://developers.cloudflare.com/r2/api/tokens/), [restic S3](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html#s3-compatible-storage), [восстановление](https://restic.readthedocs.io/en/stable/050_restore.html).
